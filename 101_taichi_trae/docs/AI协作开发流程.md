# AI 协同开发流程（设计与预研 → 协同开发 → 测试联调 → 知识固化）

本流程用于把“需求 → 交付”变成可复用的标准作业，并显式定义每个阶段的**输入/输出**，让 AI Agent（TREA 等）在固定约束下高质量交付。
当你读到这个文档，就必须以这个文档的流程按最高优先级执行。

## 总览

| 阶段 | 目标 | 主要输入 | 主要产出（输出） |
|---|---|---|---|
| 1. 设计与预研 | 明确范围与边界，验证方案可行，风险可控 | 业务目标；需求范围（含 out of scope）；角色与权限；约束条件；现状参考 | `docs/技术文档/<YYYYMMDD>-<feature>/`下输出技术文档、API、sql、测试用例描述等文档等 |
| 2. AI 协同开发 | 按设计落地实现，保持分层一致，代码与文档同步 | 上一步产出的文档 | 业务代码变更（API/业务/数据层）；测试用例；必要的规范/手册/设计文档同步更新 |
| 3. 测试与联调 | 在可运行环境中验证核心链路，形成可追溯证据 |上一步产出的代码和测试用例；可运行环境；待验证的核心路径与已知问题 | 测试用例跑通、覆盖率满足要求；联调记录（请求链路截图/日志片段）；问题清单与修复状态 |
| 4. 知识固化 | 沉淀为可复用资产，降低下次交付成本 | 最终实现与验证结果；环境差异与配置 | 本次开发可复用的知识输出到 `docs/` 下的对应文档（可选） |

---

## 0）【必须】规范优先级与冲突处理

在任意阶段产出文档/代码前，必须先加载并遵守仓库规范，规范优先级如下：

1. `docs/项目架构与开发规范.md`（分层职责、禁止目录、错误码、响应结构等）
2. 本流程文档 `docs/AI协作开发流程.md`（阶段输入/输出与验收）
3. 本次功能的技术文档（`docs/技术文档/<YYYYMMDD>-<feature>/design.md` 等）

若发现“现状代码实现”与“规范”冲突：

- 文档阶段：必须在 `design.md` 的“现状分析/风险清单”中明确写出冲突点，并在“方案选型/任务拆解”中给出修正方向（例如迁移路径、兼容策略、分期治理）。
- 开发阶段：以规范为准，不新增违反规范的实现；如确有历史包袱导致必须触碰冲突点，则在 PR/变更说明中显式记录，并同步更新规范文档（或新增例外条款）以便可追溯。

## 1）设计与预研

### 1.1 输入（你需要提供给 AI）

- 业务目标：要解决什么问题、为什么现在做
- 需求范围：包含/不包含（明确 out of scope）
- 角色与权限：谁能做什么（多租户/管理员/普通用户）
- 约束条件：性能指标、兼容性、依赖系统、上线窗口、数据迁移约束
- 现状参考：相关接口/页面/表结构/历史实现位置（路径即可）

### 1.2 【必须】输出

放置路径：`docs/技术文档/<YYYYMMDD>-<feature>/`（创建新目录）
- 技术方案文档：`design.md`
- 其他附件：`api.json`、`schema.sql` 等
- 测试用例清单：`testcases.md`
  - 用例范围：正常/边界/异常；覆盖鉴权/权限、多租户隔离、幂等与重试、状态机流转、回滚与失败重试等关键链路
  - 用例结构：用例编号、用例名称、关联接口/表、前置条件、步骤、期望结果、优先级（P0/P1/P2）、自动化计划（单测/集成/E2E/手工）

技术方案文档结构（`design.md` ）：

- 背景与目标（含 out of scope）
- 现状分析（现有模块、数据流、痛点）
- 方案选型（至少 2 个备选 + 选择理由）
  - 两个方案的详细说明：
    - 架构设计：描述完整的部署架构图和技术栈选择
    - 核心优势：突出该方案的独特价值
    - 适用场景：明确最适合使用该方案的业务场景
    - 限制条件：说明该方案的技术限制和适用边界
    - 部署复杂度：评估部署和维护的难易程度
    - 扩展性：分析未来功能扩展的可能性

  - 方案对比：
    - 制作详细的对比表格，包含但不限于以下维度：
    - 性能表现
    - 开发成本
    - 维护成本
    - 硬件兼容性
    - 安全性
    - 可扩展性
    - 对每个对比维度给出具体数据或定性分析

  - 第三方Python包推荐：
    - 列出两个方案需要用到的成熟Python包（标注必选和可选）
    - 对每个推荐包说明：
      - 核心功能
      - 性能表现
      - 社区活跃度
      - 与方案的兼容性

  - 文档格式要求：
    - 使用Markdown格式编写
    - 包含清晰的章节结构
    - 重要技术点添加代码示例
    - 关键决策点添加备注说明
    - 保持技术描述的准确性和专业性
    - 对于中英互译存在某些英文单词在翻译成中文会出现语意不顺的情况，可以用中文同义词代替，保证中文语意通顺，例如：runtime，如果翻译成运行时，中文语意不顺，可以改成运行环境/运行程序这个词等。

- 架构图（Mermaid）：组件、数据流、依赖边界
- 数据库设计：
  - 表/字段/索引/约束
  - 迁移策略（新增/变更/回滚）
  - `schema.sql`文件中，每个字段都要有中文的注释，说明字段的作用与约束
- API 设计：
  - 路径/方法/权限
  - Request/Response 示例（统一 `status/message/result`）
  - 错误码与异常场景
- 任务拆解（按文件/模块可落地）
  - 【必须】任务拆解中列出的落地路径必须符合 `docs/项目架构与开发规范.md` 的分层职责
  - 【必须】不得在任务拆解中规划把新代码落到已明确禁止/废弃的目录（例如 `myapp/views/`）
  - 若现状依赖已废弃目录：在“现状分析/风险清单”中说明，并在任务拆解中给出迁移/治理步骤（分期也可）
- 风险清单
- 验证计划（如何证明可行）
  - 列出测试用例清单（正常/边界/异常）

### 1.3 【必须】验收标准

- 是否严格按照1.2的要求输出相关文档

### 1.4 【必须】本阶段操作步骤

- 1）先阅读并抽取 `docs/项目架构与开发规范.md` 的强约束（分层职责、禁止目录、错误码/响应结构、鉴权与多租户隔离等）
- 2）按照 1.1 和 1.2 的要求输出相关文档（写入 design.md 的“约束条件/任务拆解/风险清单”）
- 3）按照 1.3 的要求，检查输出的文档是否符合要求，并额外检查“任务拆解是否违反分层与禁止目录”
- 如果上面的步骤确认没问题，则表示本阶段的任务完成，可停止，等待下一步的计划

## 2）AI 协同开发

### 2.1 输入

- 上一步骤“设计与预研输出的相关文档，放置路径：`docs/design/<YYYYMMDD>-<feature>/`
  - 技术方案文档：`design.md`
  - 其他附件：`api.json`、`schema.sql` 等
  - 测试用例清单：`testcases.md`
- 影响范围：涉及的模块与文件路径
- 约束：不新增依赖/保持错误码语义/保持响应结构/不输出密钥
- 代码规范：参考 `docs/项目架构与开发规范.md` 或设计文档的具体段落

### 2.2 【必须】输出

- 开发代码，如：
  - API层：`myapp/apis/`
  - 业务层：`myapp/biz/`
  - 数据层：`myapp/models/` + migrations（如需要）
  - 编写注释：新增代码注释量不少于30%
- 测试用例：
  - 本次步骤先编写测试用例，先不用测试联调
  - 用例必须可独立运行（见 `docs/项目架构与开发规范.md` 测试章节）
- 文档更新：
  - 若规范变更：更新 `docs/项目架构与开发规范.md`
  - 如方案细节变更，相应的`design.md`、`api.json`、`schema.sql`、`testcases.md`需要变更。

### 2.3 【必须】验收标准

- 需求对齐：是否覆盖 out of scope 以外内容
- 安全合规：是否写入/打印敏感信息，是否存在越权
- 可维护性：分层是否清晰，API 是否过厚
- 可测试性：是否补齐关键测试
- 是否补充注释：新增代码注释量不少于30%

### 2.4 【必须】本阶段操作步骤

- 1）先阅读并抽取 `docs/项目架构与开发规范.md` 的强约束（分层职责、禁止目录、错误码/响应结构、鉴权与多租户隔离等）
- 2）按照 2.1 和 2.2 的要求输出相关代码或文档
- 3）按照 2.3 的要求，检查输出的代码或文档是否符合要求
- 如果上面的步骤确认没问题，则表示本阶段的任务完成，可停止，等待下一步的计划

## 3）测试与联调

### 3.1 输入

- 上一步骤输出的实现代码、测试用例、文档等

### 3.2 【必须】输出

- 测试报告：
  - pytest 输出与 `plugin_json_report/.report.json`（如适用）
- 新增/变更 API 的测试覆盖率要求：
  - 每个新增/变更 API 接口必须提供对应的自动化测试用例（至少覆盖：正常/边界/异常）
  - 覆盖率口径：以“新增/变更 API 对应的测试用例覆盖”为主，确保关键分支（鉴权/权限、参数校验、错误码、幂等/重试、状态流转）有用例覆盖
  - 覆盖率目标：新增/变更 API 对应测试用例覆盖率 ≥ 90%（按接口维度评估；未达标需在问题清单中说明原因与补齐计划）
- 联调记录：
  - 关键请求链路截图/日志片段
  - 已知问题清单（含复现步骤与修复状态）

### 3.3 【必须】验收标准

- 无阻塞级别缺陷（P0）
- 测试用例均正常运行，无失败用例
- 新增/变更 API 接口的测试用例覆盖与覆盖率目标达成（或已明确记录未达标原因与补齐计划）

### 3.4 【必须】本阶段操作步骤

- 1）先阅读并抽取 `docs/项目架构与开发规范.md` 的强约束（分层职责、禁止目录、错误码/响应结构、鉴权与多租户隔离等）
- 2）按照 3.1 和 3.2 的要求执行。如果需要本地调试，先启动本地后端服务环境。要先按照 `docs/项目架构与开发规范.md` 中 3）启动后端（镜像运行 + 挂载本地代码）里面的内容，部署本地环境，再执行测试用例。
- 3）解决测试用例中发现的问题，直到所有用例都正常运行。
- 如果上面的步骤确认没问题，则表示本阶段的任务完成，可停止，等待下一步的计划

## 4）知识固化

### 4.1 输入

- 本次变更的最终实现与验证结果
- 线上/环境差异信息（哪些是环境特定配置）
- 最终接口规范与错误码语义

### 4.2 【必须】输出

所有固化内容建议统一归档到 `docs/design/<YYYYMMDD>-<feature>/` 目录下，方便查阅：

- 变更说明（可选）：`changelog.md`
- Runbook（排障/运维手册/运行测试用例的命令，可选）：`runbook.md`
- 更新“项目大脑”的索引与规范（可选）：
  - `docs/README.md`（新增文档入口）
  - `docs/AI协作开发流程.md`（新增可复用任务模板）

### 4.3 【必须】验收标准

- 新同事/新 Agent 只读文档即可复现开发与联调路径
- 关键决策可追溯（为什么这么做，而不是只记录做了什么）

### 4.4 【必须】本阶段操作步骤

- 1）按照 4.1 和 4.2 的要求输出相关固化文档
- 2）按照 4.3 的要求，检查输出的固化内容是否符合要求
- 如果上面的步骤确认没问题，则表示本阶段的任务完成，可停止。
- 恭喜你，完成本次的功能开发工作。
